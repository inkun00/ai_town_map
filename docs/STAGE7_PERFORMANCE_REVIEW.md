# 7단계 — 성능 측정과 파일럿 준비

측정일: 2026-09-29 · 운영 주소: https://ai-town-map.vercel.app/

## 변경과 근거

Supabase 설정 화면에서 `aimap`의 DB 지역이 `ap-northeast-2`(서울)인 것을 확인했다. 기존 API 응답의 `x-vercel-id`는 `icn1::iad1`이었다. `vercel.json`에 `regions: ["icn1"]`을 지정하여 API 실행 지역을 서울로 맞췄다. 변경 후 실제 응답은 `icn1::icn1`로 확인됐다. 기능 코드, 데이터, 권한 검사와 비공개 응답 캐시는 변경하지 않았다.

Vercel은 데이터 소스 가까이에 함수를 배치하도록 안내하며, `vercel.json`의 `regions`로 설정할 수 있다. [함수 지역 설정](https://vercel.com/docs/functions/configuring-functions/region), [지역 코드 목록](https://vercel.com/docs/regions).

- 변경 전: `7024505`
- 변경 후: `e124495` — GitHub의 Vercel 배포 성공 상태 확인
- 검증: 프로덕션 빌드/TypeScript, 스크립트 구문 검사, 실제 운영 API와 로그인된 홈·지도 조회
- 되돌리기: `vercel.json`의 지역 설정을 이전 상태로 되돌리고 재배포. DB 변경은 없어 데이터 복구 작업 불필요.

## API 결과

개발 Windows PC에서 로그인 없이 각 API 30회, 총 120회씩 순차 요청했다. 전체 응답 본문 수신까지 측정했으며 각 라운드 사이에 100ms를 뒀다. 실패는 별도 집계하고 백분위는 성공 응답에 대해 nearest-rank로 계산했다. 처음 관측한 응답을 표본에 포함했다. 사전 조회로 공개 지도를 찾으므로 통제된 콜드 스타트 검사가 아니다.

| API | 이전 p50 | 이전 p95 | 서울 p50 | 서울 p95 | 서울 최대 | 실패 전/후 |
|---|---:|---:|---:|---:|---:|---:|
| 상태 | 213ms | 281ms | 32ms | 317ms | 885ms | 0/0 |
| 공개 지도 목록 | 387ms | 451ms | 36ms | 44ms | 416ms | 0/0 |
| 지도 설정 | 1,075ms | 1,458ms | 50ms | 67ms | 84ms | 0/0 |
| 지도 분석 | 1,414ms | 1,955ms | 58ms | 77ms | 98ms | 0/0 |

지도 설정과 분석의 p95는 각각 약 95%, 96% 감소했다. 상태 API의 p95는 오히려 증가했으며 초기 응답 편차도 결과에 포함했다.

**판정: 작은 데이터의 익명 조회에서 지연 개선 확인. 전체 성능 인수 기준은 부분 검증.** 공개 지도 1개를 대상으로 했고, 변경 후 분석 대상 기록은 0건이었다. 두 측정의 각 API 최대 응답 크기는 같았다. 이 수치를 실제 사진·기록이 있는 지도, 다수 동시 참여자, 인증된 쓰기 API, 4G 환경의 성능으로 일반화할 수 없다.

원본: [변경 전 표본](qa/performance-baseline.json), [서울 배포 표본](qa/performance-seoul.json). 본문·쿠키·키·사용자 기록 내용은 저장하지 않는다. 변경 전 표본은 초기 버전 측정기의 출력이라 지도 ID/기록 수/커밋 필드가 없고, 커밋은 위에 별도 기록했다.

재측정(PowerShell, 저장 경로의 상위 폴더는 미리 준비):

```powershell
$env:PERF_ORIGIN='https://ai-town-map.vercel.app'
$env:PERF_SAMPLES='30'
$env:PERF_OUTPUT='docs/qa/performance-new.json'
$env:PERF_DEPLOYMENT='측정 대상 커밋'
# 동일 지도를 비교할 때 PERF_MAP_ID에 대상 공개 지도 UUID 지정
node scripts/measure-performance.mjs
```

## 홈 화면 관측

같은 로그인 세션의 Codex 브라우저에서 새로고침을 시작한 시각부터 ‘새 지도 만들기’ 버튼이 보일 때까지 측정했다. 기존 브라우저 캐시와 자동화 왕복 시간이 포함된 참고 관측이다. 모바일 CPU·네트워크 제한, LCP 계측 또는 지도 타일 준비 시간 측정이 아니다.

| 조건 | 관측값(ms) | 중앙값 |
|---|---|---:|
| 변경 전 5회 | 1927, 2535, 1796, 1882, 1900 | 1900ms |
| 변경 후 5회 | 1605, 8086, 289, 279, 292 | 292ms |
| API 측정 종료 후 추가 10회 | 416, 397, 292, 278, 289, 290, 276, 282, 283, 277 | 286ms |

8,086ms 관측은 제거하지 않았다. 당시 브라우저 경고·오류 로그는 없었고, API 측정 종료 후 재측정에서는 재현되지 않았다. 서버 요청 추적 자료가 없어 원인은 미확정이다. 배포 초기 상태, 인증 조회와 연결 대기, 자동화 지연을 구분하는 추가 관측이 필요하다. **4G UI 3초 목표 통과로 판정하지 않는다.**

## 파일럿 준비와 남은 조건

[파일럿 기록지](PILOT_CHECKLIST.md)에 초안 복구, 제안 기능 끄기·복원, 이모지 비활성화, 색 외 의미 확인을 추가했다. 실제 기기 결과는 실행 전까지 빈칸으로 둔다.

1. 학교 모임·일반 커뮤니티 각 1팀: Android 실기기 2대의 개설자/게스트 독립 참여, 실제 GPS·촬영·네트워크 단절·TalkBack. iOS Safari 호환성도 별도 검사한다.
2. 기록·사진이 있는 합성 지도에서 대표 데이터량별 API 성능 및 동시 참여 부하를 별도로 측정한다. 실제 4G 초기 UI와 지도 타일 준비 시간을 분리한다. 첫 로딩 편차도 보존한다.
3. 초대 실패 운영 안내: 현재 만료·철회·없는 코드·닫힌 지도는 같은 `INVITE_INVALID` 문구를 반환한다. 횟수 소진·차단·요청 제한은 별도 코드다. 교사는 관리 화면에서 초대 상태를 확인하고 새 초대를 발급하는 절차를 준비한다. 사용자 안내 개선은 후속 구현 과제다.
4. 홈은 공개/참여 지도를 각각 50개만 요청한다. 분석은 필터 결과 10,000건 초과 또는 내보내기 용량 초과 시 필터 축소를 요구한다. 규모 확대 전 목록 페이지 이동·큰 지도 처리와 실제 운영 한도를 검토한다.
5. 지도 복구·검수 기능과 별개로 장기 데이터 보관 기간, 영구 정리 작업, 백업 복원 실습은 아직 출시 조건이다. 이 작업에서 임의의 보관 기간을 정하거나 자료를 영구 삭제하지 않았다.

다음 작업은 위 남은 운영 과제의 구현과 실기기 파일럿이다. 구현은 GPT-6 Sol / High, 권한·데이터 보존 및 출시 준비 통합 검토는 GPT-6 Astra / High를 권장한다. 이번 성능 개선만으로 7단계 완료 또는 8단계 정식 출시를 선언하지 않는다.
