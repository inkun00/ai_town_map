# 3단계 구현·검토 기록

작성일: 2026-09-28 · 상태: 실제 DB·Google 로그인·독립 클라이언트 흐름 검증, 물리적 다른 기기 검증 대기

## 구현 범위

- Supabase PostgreSQL용 15개 업무·인증 테이블, 제한된 `app_backend` 로그인 역할, RLS·지도별 복합 외래키, 다섯 주제 템플릿 seed와 migration 명령을 만들었다.
- 개설자 Google OAuth PKCE, 서버 앱 세션·CSRF, 주제 조회, 지도 생성·목록·설정 조회, 초대 코드 발급·조회·폐기, 코드·닉네임 입장 API를 구현했다.
- 모바일 화면에서 실제 서버 설정이 있으면 계정 로그인·지도 생성·초대 링크 흐름을 사용하며, 환경 설정 전에는 기존 샘플 UX를 보여준다. 지도 타일·위치 포인트·사진·분석·제안은 여전히 후속 단계용 샘플이다.
- 초대 원문은 생성 시 한 번만 돌려주고 DB에는 HMAC만 저장한다. 닉네임은 권한 증명이 아니며, 입장 후 권한은 서버의 세션·membership으로 판정한다.

## 확인 결과

`npm test`에서 도메인 테스트 6개, `npm run db:check-schema`에서 SQL 구문·15개 업무 테이블·역할 권한·다른 지도 이모지 참조 거부, `npm run typecheck`와 `npm run build`가 통과했다. Supabase 관리자 DB 접속, migration 적용, 제한된 `app_backend` 계정 접속과 다섯 주제 템플릿 조회를 실제 DB에서 확인했다. `anon`의 업무 테이블 조회와 `app_backend`의 게시 템플릿 수정 권한은 없다. `/api/v1/status`는 `configured:true`다.

브라우저에서 Google 계정 세션과 실제 개설된 지도를 확인했고, 새로고침 뒤에도 지도·세션이 유지됐다. DB의 계정 principal이 Supabase `auth.users`와 연결된다. OAuth 시작은 Supabase를 거쳐 Google 도메인으로 리다이렉트된다. `scripts/check-live-phase3.mjs`로 별도 쿠키의 임시 계정·게스트를 만들어 다섯 주제 지도 생성과 핀 모드·평가 유무·이모지 선택지를 실제 DB 응답에서 확인했다. 초대 입장, 다른 비공개 지도 접근 거부, 같은 세션의 입장 재시도(uses 중복 증가 없음), 같은 닉네임의 별도 신원, 초대 폐기·만료·횟수 소진, 차단 회원 재입장 거부를 검증한 뒤 임시 지도·계정·세션을 삭제했다.

## 3단계 완료 전에 필요한 검증

1. HTTPS 테스트 주소를 준비해 초대 링크를 물리적으로 다른 기기에서 연다. 현재 `localhost`는 다른 기기에서 접근할 수 없으므로 독립 HTTP 클라이언트로만 게스트 권한을 검증했다.
2. 운영 IP 제한을 실제 배포 설정에서 확인한다. 운영 배포 전 신뢰 프록시 헤더, DB TLS 인증서 검증, OAuth 허용 URL을 확정한다.

3단계의 서버 기능과 지도 격리는 검증됐다. 물리적 다른 기기의 초대 참여와 운영 설정은 별도 검증이 필요하며, 그 범위를 완료로 표시하지 않는다.
