# 백업 복원 연습 절차

이 문서는 운영 백업의 복구 절차와 검증 기록이다. 운영 프로젝트에 일일 DB 백업이 생성된 것은 확인했다. 2026-09-30에는 운영 DB에서 `app`·`app_private` 스키마의 **논리 백업을 새로 만들어** 임시 로컬 PostgreSQL 17에 복원했다. 일일 물리 백업 자체를 복원한 검증은 아직 아니다. 운영 프로젝트를 직접 이전 시점으로 되돌리면 서비스가 중단되므로 연습 대상으로 사용하지 않는다.

## 로컬 논리 복원 검증 기록 (2026-09-30)

- PostgreSQL 17의 `pg_dump`가 운영 DB의 읽기 전용 반복 가능 읽기 스냅샷을 사용해 앱 스키마를 백업했다. 소유자 정보는 제외하고 권한 설정은 포함했다. 복원 대상은 암호를 설정한 임시 로컬 PostgreSQL 17이며, 공용 네트워크 포트를 열지 않았다.
- `pg_restore --single-transaction --exit-on-error`로 복원했다. 23개 앱·비공개 스키마 테이블의 행 수, 사진 2개의 총 바이트 및 SHA-256 해시, 마이그레이션 5개가 원본 스냅샷과 일치했다. 앱 테이블의 RLS 활성화와 정책 18개, 익명·로그인 역할의 직접 조회 거부, 서버 역할의 조회 허용 및 만료 정리 함수 실행 거부를 확인했다.
- 최종 검증은 **통과**했다. 소요 시간은 약 2분이다. 검증 스크립트가 임시 DB와 덤프를 삭제했으며 로컬 PostgreSQL 프로세스가 남지 않은 것을 확인했다. 데이터 제목·좌표·사진·인증 정보는 이 기록에 포함하지 않았다.
- 범위: 앱 스키마의 논리 백업·복원이다. Supabase의 일일 **물리 백업**, `auth` 스키마, 서비스 전체의 로그인·공개 지도·초대·삭제 복구 흐름을 복원 환경에서 검증한 결과로 해석하면 안 된다. 앱 사진은 DB의 `bytea`에 저장되므로 이번 논리 백업 범위에 포함됐다.

다시 실행할 때는 PostgreSQL 17 Windows 바이너리의 `bin` 경로를 `PG_BIN` 환경 변수로 지정하고, 무시된 `.env.migrate.local`에 읽기 가능한 `DATABASE_ADMIN_URL`을 설정한 뒤 `npm run db:check-restore`를 실행한다. 스크립트는 OS 임시 디렉터리에 격리 DB와 덤프를 만들고 정상 종료 시 삭제한다. 비정상 종료 시에는 `aimap-restore-drill-*` 임시 디렉터리와 해당 PostgreSQL 프로세스를 확인하고 데이터에 접근할 수 있는 사람을 제한한 상태에서 정리한다.

## 격리 대상 준비

### 물리 백업 복원 사전 확인 (2026-10-01)

Supabase 대시보드의 `aimap` 프로젝트에서 Pro 요금제와 `Restore to new project`의 사용 가능 상태를 확인했다. 복원은 아직 실행하지 않았다. 추가 비용이 있는 프로젝트 생성에 대한 사용자 승인을 기다린다.

- 복원 후보: 대시보드에서 확인한 최신 완료 물리 백업 `2026-09-29 16:25:35 UTC` (`2026-09-30 01:25:35 KST`). 실행 직전에 목록을 새로 확인하고 후보를 확정한다.
- 대시보드 비용: 추가 Compute 월 $9.68, 추가 Disk 월 $0, 합계 **월 환산 $9.68**. 실제 청구액·과금 기간은 생성 시점의 안내를 따른다. 동일 조직·서울 리전에 새 프로젝트를 생성하며, 디스크 크기는 원본의 1.5배로 시작한다고 표시됐다.
- 백업 시점 차이: `005_retention.sql`은 `2026-09-29 21:50:44 UTC`에 적용되어 위 백업보다 늦다. 복원 원본에는 001–004가 있을 것으로 예상하되 복원 후 직접 확인한다. 최신 운영 건수나 마이그레이션 5개를 그대로 비교 기준으로 삼지 않는다.
- 현재 운영 DB를 읽기 전용으로 확인한 결과: 활성 cron 1개(`0 17 * * *`, 앱 내부 만료 자료 정리), 앱·비공개·인증 스키마의 사용자 정의 트리거 0개, 외부 서버 0개, 활성 복제 구독 0개. `pg_net` 확장은 없고 Storage 객체도 0개다. 이 결과는 **현재 상태**이며 과거 백업의 상태를 보증하지 않는다.
- [Supabase 새 프로젝트 복원 문서](https://supabase.com/docs/guides/platform/clone-project)에 따르면 물리 복원은 cron 등의 확장 작업을 사전에 제외하거나 일시 중지할 수 없다. 복원 완료 직후 작업이 시작될 수 있으므로, 이를 허용할 수 없는 경우 CLI 논리 복원을 선택한다. 기존 절차의 ‘예약 작업 비활성 상태 확인’은 물리 복원 **이후** 점검이다.

승인 후 실행할 검증 순서는 다음과 같다.

1. 선택 백업의 시각과 새 프로젝트 식별자를 기록한다. 배포 앱의 DB·Auth 설정은 바꾸지 않고 복원 사본만 대상으로 한다.
2. 새 프로젝트에서 cron·트리거·외부 연결을 즉시 확인한다. 과거 상태를 보존할 필요가 있는 예약 작업은 사본에서 중지한다. 원본 프로젝트의 작업을 변경하지 않는다.
3. 마이그레이션 목록, 데이터 관계, 사진 바이트와 인증 사용자 존재를 백업 시점 기준으로 점검한다. 일일 백업의 원본 건수 기준표가 없으므로 최신 운영 DB와의 건수 일치를 주장하지 않는다.
4. 원본 백업 상태 검증을 기록한 뒤 사본에 누락된 마이그레이션을 순서대로 적용하고 `app_backend` 비밀번호를 별도 값으로 설정한다. 기존 운영 비밀번호는 재사용하지 않는다.
5. 로컬 앱을 복원 사본 전용 DB·Supabase 키·초대 코드 pepper에 연결한다. 연결 대상의 프로젝트 식별자를 모두 대조한 뒤 테스트 쓰기를 허용한다. 기존 `check-live-phase*.mjs`는 운영 `.env.migrate.local`을 읽으므로 격리 설정 확인 없이 실행하지 않는다.
6. Auth 공급자와 로컬 callback을 별도로 설정한 뒤 Google 로그인, 공개 지도 조회, 초대 전용 지도 차단, 코드·닉네임 참여, 합성 기록·사진 등록, 삭제 후 복구를 확인한다. 인증 설정·키는 복원에서 자동 복제되지 않으므로 DB 복원만으로 로그인 검증을 통과 처리하지 않는다.
7. 검증 기록을 남기고 임시 앱·접속 정보를 정리한다. 새 Supabase 프로젝트의 종료·삭제는 실제 생성된 대상을 확인한 뒤 처리한다. 임시 프로젝트가 남아 있는 동안 추가 과금이 계속될 수 있다.

### 공통 준비 절차

1. 복원 기능이 현재 요금제에서 별도 프로젝트로 제공되는지, 새 프로젝트·백업·데이터 전송에 비용이 생기는지 확인한다. 물리 백업을 직접 다운로드할 수 없다면 [Supabase의 백업·복원 문서](https://supabase.com/docs/guides/platform/backups)와 [CLI 논리 백업 절차](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)에 따른다.
2. 복원 대상은 공개 URL·OAuth 콜백·앱 배포·외부 알림에 연결하지 않는 격리 프로젝트로 만든다. 복원된 개인정보에 접근하는 사람을 제한한다. 새 프로젝트 생성이나 유료 기능 활성화는 비용·권한을 확인한 후 별도로 실행한다.
3. 복원 기준 백업의 생성 시각, 프로젝트 Postgres 버전, 앱 커밋과 마이그레이션 목록을 기록한다. 비밀값·개인정보·백업 파일 내용은 공개 저장소나 보고서에 남기지 않는다.

## 연습 순서

1. 격리 프로젝트에 백업을 복원한다. 물리 백업의 다른 프로젝트 복원이 허용되지 않으면, 운영 DB에서 만든 논리 백업을 안전하게 보관하고 격리 프로젝트에 `psql --single-transaction --set ON_ERROR_STOP=1`로 적용한다. 복원 중 오류를 모두 기록한다.
2. `app`, `app_private` 스키마와 마이그레이션 목록을 확인한다. 지도·기록·사진·댓글·제안서 건수, 사진 바이트 합계, 복구 가능/만료 상태를 원본의 백업 시점과 비교한다. 운영 데이터의 제목·좌표·사진 내용은 검증 기록에 복사하지 않는다.
3. 복원된 DB의 `app_backend` 역할 비밀번호를 새 비밀값으로 설정한다. Supabase 일일 백업에는 사용자 정의 역할 비밀번호가 포함되지 않을 수 있다. RLS와 `anon`/`authenticated`의 앱 테이블 접근 거부, 앱 서버 역할의 정리 함수 실행 거부를 확인한다.
4. 격리 환경에서 공개 지도 조회, 초대 전용 지도 차단, 합성 테스트 기록·사진 조회, 30일 안 삭제 자료 복구, 만료 자료 정리 함수를 확인한다. 예약된 `pg_cron` 작업이 복원 직후 외부 작업을 수행하지 않게 비활성 상태를 먼저 확인한다.
5. 검증이 끝나면 결과·소요 시간·오류·복원 가능 시점을 기록한다. 격리 프로젝트와 임시 백업의 파기 시점과 담당자를 정해 안전하게 정리한다. 실제 운영 전환은 별도 의사결정이다.

## 판정

백업 목록 존재만으로 복원 가능성을 통과 처리하지 않는다. 로컬 앱 스키마 논리 복원은 통과했으며, 일일 물리 백업과 서비스 전체 복원 검증은 별도로 남아 있다. 실제 운영 전환 전에는 격리 대상에서 인증과 앱 핵심 흐름도 확인해야 한다.
